Built to keep data for the long haul

KDSS is erasure-coded distributed storage for petabyte-scale data. We focus on one thing: keeping very large datasets safe for years at lower cost and higher reliability.

Our approach

Why we built KDSS

When data is measured in petabytes and must be kept for years, capacity is not the hard part. Two questions are: how many drives you have to buy, and whether a failed drive can cost you data.

Three-way replication is simple and dependable, but two-thirds of your drives hold duplicate copies — a cost that becomes harder to justify as capacity grows. At scale, drive failures are routine, so repair speed, upgrades without downtime and knowing how much you can still write all shape the operational burden.

KDSS replaces replication with erasure coding and a general-purpose file system with direct raw-disk writes. Detection, isolation, repair and upgrades are built into the system, so large clusters run steadily for the long term.

01

Fewer drives

29+3 erasure coding delivers 90.6% usable capacity, vs. 33.3% for 3-way replication. Sequential appends minimize seeks and help extend drive life.

02

Data that stays intact

Data stays intact through multiple failures: with 29+3, it remains readable and rebuildable with any 3 shards lost at once. Shards of a stripe never share a node, and every read is CRC-verified.

03

Simple operations

Failed drives are isolated and rebuilt automatically, and rolling upgrades need no downtime. The console shows max and conservative writable capacity, so expansion is planned, not guessed.

Technology

Built on proven, auditable components

Core services are written in Go on top of open-source building blocks proven at scale — simple to deploy and straightforward to troubleshoot.

Go

Implementation language for the Master, storage nodes, FUSE client and S3 gateway.

gRPC + Protocol Buffers

Inter-component communication, with optional mTLS.

MongoDB

A replica set holds stripe-level metadata with majority writes and backs Master leader election.

klauspost/reedsolomon

SIMD-accelerated Reed-Solomon encoding and decoding.

hanwen/go-fuse

File system layer of the ksfs FUSE client for POSIX mounts.

BadgerDB

Local shard index on each storage node.

Gin

HTTP framework for the web console and its APIs.

Zap + Prometheus

Structured logging and a full set of kdss_* metrics.

Vue 3 + Element Plus

Front end of the web management console.

Release history

Continuous delivery, calendar versioning

KDSS uses calendar versioning (CalVer): YY.MM.PATCH. For example, 26.11.2 is a November 2026 release, so you can tell at a glance how current a build is.

Recent milestones are shown here. Every release can be rolled out as a rolling upgrade (one node at a time by default), with no maintenance window.

  1. 2026 · Foundation

    Erasure coding and raw-disk engine in production

    Reed-Solomon erasure coding, sequential appends to raw disks, dual superblocks with on-disk identity, end-to-end CRC checks, and both FUSE and S3 access.

  2. Space efficiency

    Hole reuse and compaction

    Freed space is reused by new writes of the exact same size; compaction moves tail data into holes and truncates, crash-safe and verified shard by shard.

  3. Repair

    In-place repair

    After a drive replacement, data is written back to its original location on the new drive. Reads now verify stripe ID and shard index.

  4. Visibility

    Writable capacity panel and placement audit

    The console shows live max and conservative writable capacity, and a background audit continuously confirms no two shards of a stripe share a node.

  5. Operations

    Built-in alerting and hardening

    P0/P1/P2 alerts delivered via Lark and email, and bearer-token authentication for /metrics.

  6. Current release

    26.11.2

    Includes every capability listed above.
