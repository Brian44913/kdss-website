Solutions

KDSS is built for large files that are written once, kept for years and must come back intact when needed. Here is where it fits — and, for each use case, what problem it solves and how.

Sizing guide

Choosing an erasure-coding profile and cluster size

Node count determines which profiles are available: the more nodes, the higher the storage efficiency. By default KDSS picks a conservative profile for your node count automatically, so manual selection is rarely needed.

NodesProfileEfficiencyNotes
8 – 11EC 5+2tolerates 271.4%Minimum viable size, for getting started and evaluation
12 – 21EC 9+2tolerates 281.8%Small to mid-size clusters
22 – 32EC 18+3tolerates 385.7%Three parity shards; from 26 nodes, 22+3 (88.0%) can be selected manually
33+EC 29+3tolerates 390.6%Recommended for large production clusters; lowest cost per usable TB

Prefer three parity shards

During rolling upgrades, the number of nodes offline never exceeds the parity count minus one. Three-parity profiles let you maintain two nodes at a time while still leaving headroom for unplanned failures — plan for 22 or more nodes where you can.

Reference hardware

From production experience: per storage node, 36 × 16 TB enterprise HDDs (JBOD pass-through), a 20-core-class Xeon, 64 GB of memory, 2 × 10 GbE bonded and a RAID1 system disk; the MongoDB replica set on SSD.

Leave capacity headroom

New writes stop once the cluster reaches the reject line (99% by default). Plan expansion against the console's max and conservative writable figures rather than raw free space.

Production reference for a single cluster: 36 nodes × 36 disks, about 16 PB raw. For detailed planning, contact us.

Use cases

Six typical use cases

Each is laid out as challenge, approach and outcome. Decentralized storage is where KDSS already runs at scale in production; the others build on the same capabilities.

In production at scale

Decentralized storage

Sealed sector data for Filecoin and similar networks

Challenge

Sealed sectors are large and kept for long periods, so storage cost directly shapes returns. Data must also keep passing the network's storage proofs — a failed disk or machine can never make it unreadable.

KDSS approach

  • Sealing software writes through a FUSE mount; large files land sequentially
  • Large clusters run 29+3, with shards forced onto distinct nodes
  • Missing shards are decoded on the read path, so proof reads keep going
  • Rolling upgrades with no maintenance window

Outcome

  • 90.6% storage efficiency, versus 33.3% for three replicas
  • Data stays readable with any 3 shards lost at once
  • Multiple long-running production clusters, close to 190 PB raw in total
Cold data

Cold-data archiving

Imaging, logs, raw research data and other long-term records

Challenge

Data keeps growing and is rarely read, yet must be kept for years. Replication multiplies drive costs, and long retention brings silent corruption that often surfaces only when the data is finally needed.

KDSS approach

  • High-efficiency profiles (29+3, or 31+3 manually)
  • Rate-limited background CRC scrubbing finds silent corruption early
  • Recycle bin with a configurable retention window guards against accidental deletes

Outcome

  • Fewer drives per usable TB
  • Data stays online and readable at any time
  • Sequential appends reduce seeks and extend HDD life
Media

Video and media assets

Source libraries, masters and transcoded renditions

Challenge

Individual files often run to several gigabytes and reads frequently need only a segment. Editing workflows expect file paths, while distribution and transcoding systems tend to speak object APIs.

KDSS approach

  • Multipart uploads for large objects, Range reads for segments
  • Streaming I/O for large objects with bounded gateway memory
  • The same cluster can be FUSE-mounted on editing workstations

Outcome

  • File and object access share a single copy of the data
  • Standard S3 tools and SDKs connect directly
  • The library grows smoothly, node by node
Data protection

Backup and disaster recovery

S3 target for backup software

Challenge

Backup sets are large and retained for a long time, so the target itself must be dependable. Accidental deletes have to be recoverable, and a usable copy should exist in a second site.

KDSS approach

  • Target storage for S3-capable backup software, using standard multipart uploads
  • Recycle bin and GC retention window make deletes recoverable
  • For DR, deploy an independent KDSS cluster in another site and have the backup software write a second copy
  • Validate compatibility with your actual backup software before go-live

Outcome

  • Far lower drive cost for the backup target than replication
  • Multiple simultaneous disk failures don't compromise restores
  • Deletes land in the recycle bin first — an extra chance to recover
AI / Big data

Raw data lake

Training corpora, sensor and experimental data

Challenge

Raw data grows quickly and is read again and again by different compute jobs. Capacity has to be inexpensive, read throughput steady, and existing programs need direct access.

KDSS approach

  • FUSE mount lets jobs read by file path
  • Reads fetch shards from many nodes in parallel, CRC-checked throughout
  • Data pipelines can read and write through the S3 API
  • Pack large numbers of small files into larger ones to benefit from 256 MB stripes

Outcome

  • Raw data in one place, scaling out node by node
  • Every read is verified — no silent errors
  • POSIX and S3 share one copy; nothing to duplicate
On-premises

Private-cloud object storage

Your data center, standard servers

Challenge

Data has to stay in your own facility. You want object storage on standard servers, with a real management interface, access control and monitoring — not a pile of command-line scripts.

KDSS approach

  • Deploys on standard servers with JBOD drives
  • Console for buckets, access keys and users, with three-role RBAC
  • Prometheus metrics, built-in alerting (Lark, email) and audit logs

Outcome

  • Data never leaves your facility; you control deployment and growth
  • Plugs into existing monitoring with tiered alerts
  • Rolling upgrades keep maintenance invisible to applications
